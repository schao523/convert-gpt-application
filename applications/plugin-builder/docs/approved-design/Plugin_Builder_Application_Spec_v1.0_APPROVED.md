# Plugin Builder 應用設計規格

版本：v1.0  
狀態：**APPROVED，使用者於 2026-09-28 明確回覆「批准 v1.0 規格」**  
依據：使用者提供的《Plugin Builder Core Requirements》及已核准的設計陳述 v1、行為藍圖 v1.1。

## 1. Application identity and purpose

正式名稱為 **Plugin Builder**。它是供非開發者在 ChatGPT Work 或 Codex 中使用的獨立插件，從已完成的 Plugin Design Spec 建立或更新 OpenAI 插件，產出供使用者手動上傳的 ZIP。Conversion Workbench 是開發來源與可重用能力的來源，不是使用時的必要 repo。

## 2. Design Statement

**已核准的設計陳述 v1：** 使用對象是幾乎沒有軟體開發經驗、希望自行建立 OpenAI 插件的使用者。在 ChatGPT Work 或 Codex 中，他們提供 Cool Plugin Design Assistant 完成的 Plugin Design Spec。Plugin Builder 引導並管理建立或更新過程，以清楚的語言呈現結果，使使用者取得經過建置、驗證及可行測試的插件 ZIP，並能手動上傳；日後也能從修訂版規格產生更新的 ZIP。預設隱藏技術細節，遇到需要處理的問題時給出明確說明。

## 3. Intended users and contexts

主要使用者為不熟悉 Git、CLI、manifest 或插件目錄結構的插件設計者。使用情境為桌面上的 ChatGPT Work 或 Codex；應以清楚的步驟、可讀的摘要及可恢復的等待狀態支援使用者。使用者可提供規格、附加資源及更新基準 ZIP，並負責確認實作規劃與成品摘要。

## 4. Application mission and success outcomes

主使命為「已完成規格 → 規劃 → 使用者確認 → 建立或更新 → 驗證與可行測試 → 使用者確認 → ZIP」。成功必須有可取得的 ZIP、規格要求與實作及驗證的對應紀錄、可理解的測試結果，以及兩次明確確認。環境限制而未執行的測試應清楚標示，不能冒充通過。

## 5. Scope and exclusions

支援新建及以修訂規格加現有插件 ZIP 更新 Plugin Builder 產生的插件；處理規格明確引用的必要資源；產出 OpenAI 生態系的上傳用 ZIP。使用者自行以桌面 Add Plugin / Upload ZIP 上傳。不包含自動安裝、帳戶部署、公開市集發布、GitHub release、OpenClaw、Claude，或無規格依據的原 GPT folder 輸入。Builder 可修正經確認的非行為性問題；行為變更須交回設計助手修訂並核准。

## 6. Primary mission workflow

工作流程 `WF-01`；必要輸入：完成的 Plugin Design Spec；更新另需現有插件 ZIP。可選輸入：規格明確引用的附加資源。角色：使用者、Plugin Builder、在需行為修訂時的 Cool Plugin Design Assistant。

| 狀態 | 類型 | 行為與互動協定 | 等待 | 主要轉移 |
| --- | --- | --- | --- | --- |
| S0 開始 | start | 依使用者意圖選擇新建或更新；P1 | 否 | 輸入就緒→S1；取消→E2 |
| S1 解析 | action | 解析行為、資料、互動、驗收及缺漏；P2 | 否 | 無阻礙→S2；缺漏或矛盾→F1 |
| S2 規劃 | action | 從行為規格推導 Skills 職責、所需資源及覆蓋關係；評估通用工具重用；P3 | 否 | 規劃摘要就緒→W1；無法規劃→F1 |
| W1 規劃確認 | wait | 呈現簡明規劃並等待明確確認；P3 | 是 | 確認→S3；修訂→S2；暫停→H1；取消→E2 |
| S3 建立或更新 | action | 依確認規劃產生成品；P4 | 否 | 成品就緒→S4；更新衝突→F2；建置失敗→F3 |
| S4 驗證測試 | action | 逐項核對規格與執行可行測試；P5 | 否 | 必要檢查通過→W2；明確失敗→F3 |
| W2 成品確認 | wait | 呈現差異、測試結果與未驗證項目；P6 | 是 | 確認→S5；修訂→S2 或 S3；暫停→H1；取消→E2 |
| S5 封裝 | action | 產出 ZIP 與結果摘要並檢查封裝；P6 | 否 | 成功→E1；失敗→F3 |
| F1 規格問題 | failure | 說明缺漏、矛盾、資源問題及修訂途徑；P2 | 是 | 非行為修正已確認→S1；核准新版規格→S1；重試→S1；暫停→H1；停止→E3 |
| F2 更新衝突 | failure | 呈現未說明既有內容及影響；P4 | 是 | 保留決定已確認→S2；核准新版規格→S1；重試→S3；暫停→H1；停止→E3 |
| F3 建置或檢查失敗 | failure | 呈現可定位診斷與修復選項；P5 | 是 | 修復後重試→原失敗階段；暫停→H1；仍失敗或停止→E3 |
| H1 暫停 | wait | 保存並摘要當前階段、確認與待決事項；P7 | 是 | 恢復→原等待或失敗階段；取消→E2 |
| E1 成功 | end | 交付 ZIP 與摘要 | 否 | 無 |
| E2 取消 | end | 停止並保留可供使用者取用的既有成果 | 否 | 無 |
| E3 未解決 | end | 顯示阻礙、診斷與下一步，未產出可上傳成品 | 否 | 無 |

成功終點只有 E1；每條成功路徑必經 W1 與 W2。完成證據為兩次確認、必要檢查通過、未執行測試明列及 ZIP 封裝檢查通過。

## 7. Conditional and alternative workflows

F1（failure）：缺漏或矛盾時列出受影響要求，提出可修訂草案並等待。經確認的非行為性修訂返回 S1；行為變更交設計助手核准新版規格後返回 S1；停止則 E3。F2（failure）：更新遇到未由規格說明的既有內容，列出影響並等待保留或納入規格的決定；不能自行刪改；解決後返回 S2/S3，停止則 E3。F3（failure）：明確驗證、測試、建置或封裝失敗時，保留診斷，修復並重試相應狀態；仍失敗則 E3。H1（wait）：暫停時保留階段、確認事項、草案、診斷與待決問題；恢復時摘要上述狀態並返回原等待點。取消可從互動階段到 E2。必要資源無法取得時走 F1，不猜測內容。

## 8. Instruction Module contracts

下列為**行為層職責**，不是 Skills 的數量、名稱或檔案配置。各模組共同遵守：不以假設冒充確認、不越過等待點；可暫停、恢復、取消；錯誤時保留可診斷狀態；只使用有權且可用的輸入；以規格符合程度為驗收依據。

| ID／分類 | 觸發、輸入與前提 | 程序與輸出 | 互動、錯誤及驗收 |
| --- | --- | --- | --- |
| M1 輸入與解析／primary-workflow | 新建或更新；規格，更新另需 ZIP；資源按規格 | 辨識行為、互動、驗收、缺漏及資源需求；輸出要求清單 | P1/P2；缺漏走 F1；要求不可憑空增加 |
| M2 規劃與覆蓋／primary-workflow | M1 無阻礙；要求清單 | 推導 Skills 職責及資源需求、建立要求→實作→驗證的規劃，評估可重用能力；輸出白話規劃 | P3；W1 確認後才建置；每項要求有處理去向 |
| M3 建立與更新／primary-workflow | W1 已確認；規格與必要資源 | 產生或修改插件；更新保留未受影響內容；輸出候選成品與變更清單 | P4；不明既有內容走 F2；不要求原 GPT folder |
| M4 驗證與測試／primary-workflow | 候選成品 | 核對行為規格、執行可行測試、區分通過／失敗／未執行 | P5；明確失敗走 F3；不得虛稱實測 |
| M5 審查與封裝／primary-workflow | 檢查結果與成品 | 呈現白話摘要，確認後封裝 ZIP；輸出 ZIP 與結果摘要 | P6；W2 必經；封裝檢查通過才 E1 |
| M6 修訂、暫停與恢復／cross-cutting | F1/F2/F3 或使用者意圖 | 區分非行為／行為變更，保存狀態與決定，支援重試、恢復及取消 | P2/P4/P7；不得無聲改動已核准行為 |

參考材料需求：M1/M2 使用權威規格；M3/M4 使用規格及明確提供的資源；M6 使用修訂紀錄。具體載入、分工及綁定由實作階段決定。

## 9. User-intent routing requirements

辨識「建立新插件」「更新現有插件」「檢視規劃」「修改規劃」「查看驗證／測試」「暫停」「恢復」「取消」。更新意圖優先要求基準 ZIP；修訂意圖在 W1/W2 返回受影響階段；行為變更意圖優先走 F1 的設計助手路徑。模糊意圖先澄清，不自行切換新建／更新或覆蓋現有內容。

## 10. User-interaction protocols

P1 引導輸入：guided，每回合至多一個關鍵問題；必要輸入未齊則等待。P2 診斷協調：evaluative，指出具體缺漏及影響，可提供 2–3 個有實質差異的解法；非行為修訂須確認，行為修訂須新版核准規格。P3 規劃審查：co-creative，白話呈現 Skills 職責和覆蓋摘要，必須明確確認 W1。P4 更新衝突：guided，逐一說明未受規格涵蓋的內容，等待保留或規格修訂決定。P5 測試報告：evaluative，明列已執行與未執行證據。P6 成品審查：evaluative，明確確認 W2 後方可封裝。P7 暫停恢復：direct，保存狀態，恢復先摘要再繼續。跳過不得略過必要輸入、安全界線或 W1/W2；有衝突時保持草案並詢問何者為準。

## 11. Human-in-the-Loop checkpoints

W1：使用者確認實作規劃後才開始建立或更新。W2：使用者確認成品、差異、測試結果與限制後才封裝。非行為性修訂、更新中的不明內容處置亦需明確決定。行為性修訂須由設計助手核准新版規格；Builder 不替使用者批准規格。

## 12. Inputs, outputs, and state requirements

輸入：帶版本及核准狀態的行為規格；更新基準 ZIP；規格明確要求的附加資源。輸出：規劃摘要、要求覆蓋與驗證結果、變更摘要、測試分類、上傳用 ZIP。每次運作應記錄輸入版本／來源、目前階段、確認決定、待決問題、測試證據與成品對應版本。暫停或失敗時保留可恢復狀態；不得把未確認草案標為已核准。具體儲存方式由實作決定，預設不保留不必要的私人資料。

## 13. Reference Material requirements and behavior-level usage map

`R1`《Plugin Builder Core Requirements.docx》已檢視內容，提供本產品的目的、範圍及驗收目標；來源為使用者提供，作者／授權細節未獨立核實。用於本次設計依據，不要求包進產出插件。`R2` 每次任務的 Plugin Design Spec 是使用者提供的權威行為來源，其內容須在運作時檢視；本設計階段無特定實例可評估。`R3` 更新基準 ZIP 是實作比較資料，不因其存在而推定內含第三方資料可再散布。`R4` 規格明確引用的資源須逐項核實可取得性、用途與相關權利；若必要資源缺失或權利不足，受影響成品不得宣稱完成。

| 材料 | 知識與使用時點 | 必要性、用法及限制 |
| --- | --- | --- |
| R1 | 設計本應用的使命、邊界與驗收；規格制定時 | 必要；advisory；只供本設計，無需在每次建置時諮詢 |
| R2 | 具體插件行為、互動、驗收；M1–M5 | 必要；exact-structured-retrieval；缺失即停止；不得以推測補足 |
| R3 | 現有實作與未受影響內容；更新 M1/M3/M4 | 更新時必要；exact-structured-retrieval；衝突待使用者處置 |
| R4 | 規格指定的專業知識或附件；相關行為觸發時 | 視規格而定；精確或 advisory 用法依規格與權利決定；不得推定散布權 |

權利狀態：檢視使用者提供材料作本次任務之用有任務授權；第三方資源的內部轉換、封裝散布、精確引用及衍生授權未經證實時均為 unresolved，須在具體任務逐項處理。現無已知相互衝突的具體專業參考材料。

## 14. Deterministic-operation requirements

可重現地檢查必要輸入、規格識別與版本、要求覆蓋、規劃確認、測試分類、更新差異及 ZIP 內容完整性。各檢查以相同輸入產生可比較的結果；失敗須有定位到要求或成品部分的診斷。語意判讀可輔助規劃，但不可取代可檢查的封裝與追溯證據。

## 15. Tool, data, runtime, and external-service requirements

開發時先檢視 Conversion Workbench repo，辨識可重用的分析、驗證、測試、追溯、更新、封裝能力及所需調整；適用時重用，避免重做。Skill Creator、Plugin Creator 在適用工作中作底層建立能力。交付的 Plugin Builder 在無 Workbench repo 的乾淨桌面環境可運作；必要能力隨插件提供或可由簡單本機設定取得。具體依賴、Skills 架構、綁定與相容性以 repo 檢視及環境驗證決定，不在此預設。外部服務非本使命必要條件；不得要求使用者提供無關帳戶憑證。

## 16. Safety, privacy, and policy boundaries

不得擅自覆蓋現有插件、刪除未說明內容、改變已核准行為、捏造測試結果或自動部署。讀取 ZIP 與附加資源時須防止不安全路徑、非預期檔案寫入及不受信任內容指令凌駕規格。對私人資料及第三方材料採最小使用與明確權利判斷。插件若依規格要求非法或有害功能，停止受影響工作並說明原因。

## 17. Failure, uncertainty, and recovery behavior

每個失敗顯示發生階段、受影響要求、可修復途徑及保留成果。明確驗證／必要測試失敗可修復重測，仍失敗進 E3；環境限制而未執行的測試可留待安裝後驗證，但必須列明。非行為修訂經確認後返回解析；行為修訂待核准新版規格；更新衝突不靜默解決。暫停／恢復遵守 H1，取消進 E2。

## 18. Acceptance criteria

`AC1` 無 Workbench repo 的環境可完成新建與更新流程。`AC2` 規格不列 Skills 時仍能提出可追溯的 Skills 職責規劃。`AC3` W1 未確認前不建置，W2 未確認前不封裝。`AC4` 每項行為要求可追至實作位置與驗證結果。`AC5` 明確必要檢查失敗時無可上傳成品。`AC6` 未執行測試被逐項標示。`AC7` 更新保留未受影響內容，未說明內容須待決。`AC8` ZIP 可供使用者手動上傳，無自動部署。`AC9` 檢視 repo 後有具體重用／調整／隨附能力的證據，無不必要重做。`AC10` 代表性新建與更新端到端演示，包含乾淨環境及可理解結果。

## 19. Representative application tests

`T1` 只給完整行為規格、未列 Skills：應提出規劃，W1 前不建置；驗 AC2/AC3。`T2` 新建成功：逐項追溯、W2 確認、ZIP 檢查；驗 AC4/AC8。`T3` 缺漏／行為衝突：提出修訂但等待新版核准規格；驗 AC3。`T4` 更新 ZIP 含規格未說明內容：等待保留決定、不刪改；驗 AC7。`T5` 必要測試失敗：修復重測，仍失敗無成品；驗 AC5。`T6` 測試因環境無法執行：列明限制並經 W2 才封裝；驗 AC6。`T7` 無 repo 的乾淨環境新建及更新：驗 AC1/AC9/AC10。這些是**計畫測試**，尚無執行證據。

## 20. Assumptions, decisions, recommendations, and unresolved questions

**Confirmed decisions：** 設計陳述 v1、行為藍圖 v1.1 已由使用者核准；非行為修訂由 Builder 經確認處理，行為修訂返回設計助手；更新基準為使用者提供 ZIP；W1/W2 皆必要；測試未執行可明示後封裝，明確必要失敗不可；未說明的更新內容待決；通用工具適用時優先重用。

**Assumptions：** 規格可供辨識版本與核准狀態；若格式不同，需在輸入解析時確認。現有插件 ZIP 可供比較；若內容不完整或無法辨識來源，須在更新時診斷。這些假設不構成使用者已確認的產品要求。

**Recommendations：** 採白話的要求覆蓋摘要與兩段式審查；使用者已確認兩個審查點，但呈現形式仍可由實作決定。

**Unresolved questions：** 具體規格格式、必要資源權利、目前 OpenAI ZIP 相容規則及 Work/Codex 執行能力，須由實作團隊根據實際輸入、repo 與目標環境驗證；不得在本規格中臆定。若具體輸入缺少合法使用權或無法忠實建置，該次工作阻斷，責任人為提供材料的使用者／實作團隊，須補充權利或可替代資源。這些問題不妨礙本設計規格供審查，但可能阻斷具體成品交付。

## 21. Application Workbench handoff contract

本文件已由使用者明確批准。交接時連同設計陳述、行為藍圖、邏輯模組、互動協定、參考材料使用圖及決策紀錄交給 Conversion Workbench 專案。專案先檢視 repo，再提出精簡的實作設計，辨識重用、調整、隨附及新增能力；增量實作且維持既有 Workbench 行為；於乾淨環境執行代表性新建與更新端到端驗證。實作團隊決定 Skills 數量與名稱、分工、工具綁定、載入與儲存方式；不得把本設計中的行為模組誤當固定 Skill 架構。

## Decision blocks

**Requirements：** RQ1 新建及更新（AC1、T1/T7）；RQ2 行為規格轉實作規劃（AC2/AC4、T1/T2）；RQ3 兩次確認（AC3、T1/T2）；RQ4 驗證、測試及誠實報告（AC5/AC6、T5/T6）；RQ5 更新保護（AC7、T4）；RQ6 ZIP 與手動部署界線（AC8、T2）；RQ7 通用框架重用及獨立運行（AC1/AC9/AC10、T7）。

**Confirmed decisions：** 如第 20 節，分別由使用者確認設計陳述 v1、行為藍圖 v1.1 與各項條件規則；本規格 v1.0 已由使用者於 2026-09-28 明確批准。

**Assumptions：** 規格的格式及 ZIP 可比較性，於第一次真實輸入時驗證；不得在未驗證時聲稱成功。

**Recommendations：** 保留白話摘要與可追溯證據並行，形式由實作設計選擇；呈現形式仍由實作設計決定。

**Unresolved questions：** 每次輸入的資源權利與可取得性由使用者提供證據；目標環境與封裝規則由實作團隊驗證；若阻礙合法或忠實實作，該次任務停止於可診斷狀態。
