# Framework and Marketplace Hardening Design

## 1. Executive Summary

The conversion framework can build deterministic plugin bundles, but its
current distribution-contract schema does not classify every packaged file or
define checkout-stable byte policies. Marketplace validation is also partly
product-specific: Vibe Coding Designer has an isolated job, while the older
Cool Bible Tutor job still owns hard-coded marketplace assertions and a
ClawHub dry run that is incompatible with its bundle-only package.

This change hardens the generic Python 3.11+ framework and its marketplace
tooling. It introduces distribution-contract schema v3, canonical content
policies, structured non-interactive recovery diagnostics, transactional
marketplace preparation, Git-blob verification, and catalog-driven CI. The
framework remains a library and CLI. It does not become, or design, a
Conversion Workbench plugin; it only establishes stable machine-readable
boundaries that such a future plugin could consume.

Vibe Coding Designer is the first real schema-v3 and generic-CI integration
case. Cool Bible Tutor remains a separate legacy migration after the generic
capability is complete.

## 2. Goals and Non-goals

### Goals

- **FRH-001:** Require schema v3 for every newly built distribution while
  retaining schema v1 and v2 as read-only legacy formats.
- **FRH-002:** Require every final package file to have exactly one content
  classification and canonical byte policy.
- **FRH-003:** Stop before output replacement when a file is unclassified,
  ambiguously classified, unsafe, or missing a required rights decision.
- **FRH-004:** Return versioned, machine-readable results and diagnostics for
  validation, migration, build, marketplace preparation, and verification.
- **FRH-005:** Produce marketplace deltas transactionally without silently
  mutating an existing marketplace checkout.
- **FRH-006:** Verify generated bytes in the staging tree, Git index, committed
  tree, and a clean checkout under Windows, Linux, and macOS semantics.
- **FRH-007:** Generate marketplace CI from marketplace catalogs so every
  registered plugin is independently validated on every supported operating
  system.
- **FRH-008:** Keep GitHub marketplace and ClawHub admission as distinct,
  explicitly declared publication contracts.
- **FRH-009:** Keep generic framework behavior application-neutral and leave
  domain behavior, product audits, and runtime acceptance tests with the
  owning application.
- **FRH-010:** Make the public Python and CLI contracts usable by an
  independently distributed client or orchestrator without developer-local
  paths or repository-relative hidden state.
- **FRH-011:** Require no human identity, interactive prompt, or human-only
  execution path; authorization is represented by explicit approved inputs.

### Non-goals

- Converting Conversion Workbench into a plugin or designing its skills,
  launchers, setup flow, or interactive recovery experience.
- Bundling the framework, a Python runtime, or a private environment into a
  redistributable Workbench plugin.
- Repairing or migrating Cool Bible Tutor as part of the generic framework
  change.
- Changing the behavior, skills, or approved content of Vibe Coding Designer.
- Inferring redistribution permission, accepting a suggested classification
  automatically, or rewriting an application contract in place.
- Modifying original GPT source archives.
- Publishing, pushing marketplace changes, creating tags or releases, or
  submitting to ClawHub.
- Downloading models, corpora, release assets, or large dependencies.

## 3. Users and Actors

- **Conversion caller:** invokes the public Python API or CLI and supplies
  explicit inputs. A caller may be a coding agent, CI job, script, future
  Workbench plugin, or human operator. Calling the framework does not grant
  authority to invent scope, rights, or publication decisions.
- **Decision owner:** is the person or organization authorized to approve
  application scope, file classifications, redistribution rights, target
  runtimes, and publication. Owner decisions are recorded in application-owned
  contracts or provenance before an automated caller applies them.
- **Application workspace:** owns product files, distribution rules, rights
  records, product audits, and behavioral tests.
- **Generic framework:** validates declarations, canonicalizes approved files,
  builds artifacts, prepares deltas, and emits evidence. It has no authority
  to make product or rights decisions.
- **Client or orchestrator:** is an optional conversion caller that may
  translate structured diagnostics into guided interaction. It must submit
  explicit, already approved inputs back to the framework and cannot treat a
  framework suggestion as owner approval.
- **Marketplace repository:** owns public catalogs, generated plugin artifacts,
  CI workflows, and release metadata. It is an explicit input or staged
  destination, never an implicitly discovered writable location.
- **Git:** provides index, tree, and checkout byte evidence. Local Git commands
  are permitted; network operations are outside this design.
- **GitHub Actions:** runs the generated cross-platform marketplace matrix.
- **ClawHub:** is a separate optional publication target. The framework does
  not treat a valid bundle-plugin package as proof of ClawHub admission.

The framework trusts only validated configuration and confined local paths.
It validates that required decision evidence exists, but it cannot identify
whether its caller is human or verify the legal authority of a decision owner.
Source files, product hooks, marketplace contents, and Git output remain
untrusted inputs until their applicable checks pass.

## 4. Use Cases and Flows

### Validate a schema-v3 contract

The conversion caller supplies a contract. The framework validates its schema,
identity, path confinement, selection rules, content policies, rights
declarations, publication declarations, and application manifest. Success
returns a `PASS` result without writing an artifact. A recoverable missing
decision returns `BLOCKED`; malformed or unsafe input returns `FAIL`.

### Recover from an unclassified file

The framework inventories the files selected by the distribution contract and
finds one with no unique policy. It stops before staging or output replacement
and emits `unclassified_files`. The diagnostic contains the relative path,
detected characteristics, candidate classifications, required contract fields,
and applicable dispositions: packaged text, packaged binary, excluded,
external asset, or private/local-only. Suggestions are advisory. The decision
owner approves the disposition; a conversion caller then records that approved
decision and reruns validation.

### Migrate a legacy contract

The conversion caller supplies a schema-v1 or schema-v2 contract and a distinct
output path. The framework parses the legacy contract, inventories its selected
files, and writes a proposed schema-v3 contract only when the destination does
not already exist. Any unresolved classifications or rights declarations are
represented in diagnostics, not guessed in the proposal. The source contract
is never overwritten. Legacy contracts remain valid inputs only for inspection
and legacy artifact verification; build and marketplace preparation return
`legacy_contract_read_only`.

### Build and verify a package

After schema-v3 validation, the builder canonicalizes text, preserves binary
bytes, generates canonical JSON, runs generic and product audits, and creates a
content manifest in a temporary sibling directory. Only a fully successful
build replaces the requested output. Verification recomputes the manifest from
the final bytes and rejects any difference.

### Prepare and verify a marketplace delta

The conversion caller supplies application configurations, a marketplace
catalog or checkout, and an output staging root. The framework builds the
declared schema-v3 Codex and OpenClaw artifacts, preserves and verifies any
legacy `verify_existing` artifacts without rebuilding them, updates staged
catalogs and per-plugin Git attributes, generates generic CI, and writes a
delta report. The source marketplace remains unchanged. Verification checks
staged bytes and, when explicitly given a Git index or commit, compares exact
blob bytes and a clean-checkout result.

### Validate marketplace CI

The generated workflow derives or consumes a checked-in matrix that contains
every plugin registered in the required catalogs. Each plugin/OS cell runs
generic artifact checks and that plugin's declared product commands. Failures
are isolated for diagnosis, but any required failing cell fails the aggregate
marketplace gate.

## 5. Software Form and System Boundaries

The product remains the `obvious_one_plugin_framework` Python package and its
`obvious-one-plugin`/module CLI. It has no Web, desktop, or interactive terminal
interface.

The conversion repository owns:

- public framework modules under `src/obvious_one_plugin_framework`;
- generic framework and repository-contract tests;
- schema and marketplace templates;
- application workspaces and their test declarations;
- generated output only below ignored `dist` or `.tmp` roots.

An application owns its domain files, audit hook, assets, indexes, behavioral
tests, and runtime evidence. The marketplace owns its checked-in artifacts,
catalogs, `.gitattributes`, generated verifier, workflows, and release policy.

The framework may prepare a complete marketplace delta in a separate staging
root. Applying that delta to a marketplace checkout is a later, explicitly
authorized operation and is not part of `prepare-marketplace`.

## 6. Interface Specification

### Public CLI

All commands are non-interactive and emit exactly one JSON result document to
standard output. Progress and diagnostic prose, if any, go to standard error
and must not be required to interpret the result. Paths in distributable
reports are repository- or artifact-relative; private absolute source paths are
never serialized.

The CLI retains `build-assets`, `check-index-reuse`, and `derive-index` and adds
or hardens these commands:

```text
validate-contract --contract PATH
migrate-contract --contract PATH --output PATH
build-package --contract PATH --output PATH
verify --contract PATH --output PATH
prepare-marketplace --catalog PATH --marketplace PATH --output PATH
verify-marketplace --catalog PATH --marketplace PATH [--index|--commit REF|--fresh-checkout]
report --inputs PATH... --output PATH
```

`prepare-marketplace` treats `--marketplace` as a read-only baseline and
`--output` as a new or replaceable staging destination. It refuses identical,
nested, root, repository-root, or otherwise unsafe source/destination paths.

Every command uses result schema version 1:

```json
{
  "result_schema_version": 1,
  "operation": "build-package",
  "status": "BLOCKED",
  "code": "unclassified_files",
  "diagnostics": [],
  "artifacts": [],
  "mutations": []
}
```

Statuses are `PASS`, `BLOCKED`, and `FAIL`. Evidence fields use `EXPECTED`,
`STATICALLY VERIFIED`, `RUNTIME VERIFIED`, and `NOT VERIFIED`; individual gates
use `PASS`, `FAIL`, `NOT VERIFIED`, and `NOT APPLICABLE`.

Exit codes preserve the existing command families:

- `0`: operation passed;
- `2`: contract, invocation, or policy error, including a recoverable blocked
  decision;
- `3`: build, audit, or verification failure;
- `4`: I/O or local environment failure.

The JSON status and code, not the exit code alone, distinguish `BLOCKED` from
`FAIL`. CLI syntax errors must also use the result envelope rather than raw
`argparse` prose alone.

### Public Python API

Public, documented symbols provide the same operations as the CLI:

- `load_contract` and `validate_contract`;
- `migrate_contract`;
- `build_package` and `verify_package`;
- `prepare_marketplace` and `verify_marketplace`;
- report models and deterministic JSON serialization.

Public APIs return typed immutable result objects or raise documented framework
errors with stable codes. Marketplace code must not import underscore-prefixed
helpers. Provider APIs, runtime executable paths, credentials, and UI concerns
must not enter these contracts.

## 7. Component Architecture

### Contract model and version router

Parses schema versions without conflating them. Schema-v1 and schema-v2 models
support read-only inspection and legacy verification. Schema v3 is the only
build-capable model. The router returns `legacy_contract_read_only` before a
legacy contract can reach a builder.

### Inventory and policy engine

Expands safe POSIX-relative selectors, rejects links and reparse points, and
assigns exactly one policy to each candidate. A schema-v3 file policy declares:

- one or more safe relative patterns;
- a disposition: `package`, `exclude`, `external_asset`, or `private_local`;
- for `package`, content kind `text` or `binary`;
- a rights decision and non-secret provenance reference appropriate to the
  disposition.

Zero policy matches produce `unclassified_files`; multiple matches produce
`ambiguous_file_classification`. An included or externally distributed file
without an affirmative rights declaration produces `rights_unresolved`.

### Canonical content engine

Application text is strict UTF-8 without a byte-order mark and is written with
LF line endings. It otherwise preserves content, including whether the source
has a final newline. Binary content is copied byte-for-byte. Framework-generated
JSON uses sorted keys, UTF-8 without a byte-order mark, LF line endings, stable
indentation, and exactly one final newline. Framework-supplied runtime files
carry built-in framework policies rather than application-owned rules.

### Artifact builder and verifier

Builds in a temporary sibling directory, applies overlays before auditing,
runs the existing generic secret/size/link checks and optional application
audit, creates the manifest, and atomically replaces output only after success.
The manifest records each final relative path, classification, canonicalization
policy, size, and SHA-256, plus the aggregate content identity.

### Marketplace preparer

Consumes marketplace catalogs and application distribution contracts, invokes
the canonical builders, and creates a complete staged delta. It updates only
declared plugin paths and generated marketplace control files. It emits
plugin-specific exact-byte `.gitattributes` rules such as
`/plugins/<id>/** -text` and `/openclaw/<id>/** -text`; it must not change
unrelated repository paths.

### Git evidence verifier

Compares the artifact manifest with working-tree bytes, `git ls-files --stage`
and `git cat-file` index blobs, a selected commit tree, and an isolated fresh
checkout. It verifies the applicable attributes with `git check-attr` and
reports path-level differences without rewriting any checkout.

### CI generator and self-contained verifier

Generates a stable plugin-by-OS matrix from all required catalog entries. The
marketplace receives a lightweight verifier derived from public framework
contracts so CI does not depend on a developer checkout of this repository or
on product-specific hard-coded assertions. Application commands remain
catalog/configuration data and execute only for their owning plugin.

These components may depend inward on contract and result models. Product
modules must not be imported by generic code except through a declared audit or
command boundary. Cool Bible Tutor identifiers, Bible-domain behavior, and
Vibe-specific acceptance rules are prohibited in generic production modules.

## 8. Data and Persistence

### Distribution-contract schema v3

Schema v3 retains product identity, size, release, optional RAG, overlay, and
audit declarations while replacing implicit byte behavior with explicit file
policies and publication declarations. The existing schema-v2 fields remain
unless replaced below. Schema v3 adds these required objects:

```json
{
  "schema_version": 3,
  "content_rules": [
    {
      "id": "portable-text",
      "paths": ["README.md"],
      "prefixes": ["docs", "skills"],
      "classification": "text",
      "redistribution": {
        "status": "approved",
        "provenance": "docs/source-decisions.md"
      }
    }
  ],
  "publication": {
    "github_marketplace": {"enabled": true},
    "clawhub": {
      "enabled": false,
      "family": null,
      "native_manifest": null
    }
  }
}
```

`paths` and `prefixes` contain normalized POSIX-relative values with the same
escape and duplicate protections as the existing include selectors. A prefix
matches only descendants at path-segment boundaries. Every final
application-owned package path selected by `include_files` or
`include_prefixes`, after exclusions and overlay destination mapping, must
match exactly one content rule. `classification` is exactly `text` or
`binary`. Framework-generated files and framework-vendored runtime files use
versioned built-in rules and cannot be reclassified by an application.

Every packaged application rule requires `redistribution.status` equal to
`approved` and a nonempty, safe, source-root-relative provenance path. The
framework confirms the provenance file exists but does not interpret its legal
sufficiency. The decision owner chooses how a non-distributable discovery is
handled. A conversion caller then records that approved choice by changing the
explicit selection boundary: `exclude_paths` for excluded or private-local
material, or the existing declared asset-group mechanism for an approved
external asset. Diagnostics describe these alternatives but do not apply them.

GitHub marketplace publication may be enabled independently. ClawHub defaults
to disabled. Enabling ClawHub requires an explicit supported family and the
safe relative path of the native manifest required by that family; absence or
incompatibility is a validation failure, not a skipped dry run. When ClawHub is
disabled, `family` and `native_manifest` must be null.

`migrate-contract` writes a proposal document rather than claiming that
inferred decisions form a valid contract. Its output contains
`proposal_schema_version: 1`, `target_schema_version: 3`, a `contract_draft`,
and structured `diagnostics`. The draft becomes a buildable contract only
after all diagnostics are resolved and normal schema-v3 validation passes.

### Content manifest

The content manifest advances to a new schema that records:

- plugin and version identity;
- file count, total bytes, and aggregate content digest;
- for every file: relative path, content classification, canonicalization
  policy, byte size, and SHA-256.

Manifest ordering is lexical by POSIX relative path. Aggregate identity is
calculated from the canonical compact JSON representation of ordered file
records, excluding the manifest itself.

### Marketplace catalog and reports

Existing Codex and OpenClaw catalogs remain authoritative for registration.
The preparer validates one-to-one identity and version agreement across the
catalogs, plugin manifests, distribution contracts, and content manifests.
Generated CI matrix data is derived from those catalogs and may be committed as
a generated control file when the workflow cannot derive it directly.

The `--catalog` argument names a preparation catalog, not either public
runtime catalog. Preparation-catalog schema version 1 contains a marketplace
identity and an ordered `applications` array. Each application entry contains:

- a safe catalog-relative path to its `conversion.json` and distribution
  contract;
- its intended Codex and OpenClaw marketplace destinations; and
- `mode`, which is exactly `build` or `verify_existing`.

`build` requires a schema-v3 distribution contract and may generate replacement
artifacts. `verify_existing` accepts a schema-v1, schema-v2, or schema-v3
contract only for inspection, CI registration, and verification of artifacts
already present in the marketplace baseline; it must not invoke a builder,
replace bytes, or update that plugin's catalog identity or version. This mode
allows a legacy plugin to remain covered by generic marketplace CI while its
product migration is deferred.

Product descriptions, categories, versions, build commands, and validation
commands continue to come from their existing application-owned declarations.
An application validation command opts into marketplace execution through the
optional `marketplace_targets` array on its existing command object. Allowed
values are `codex` and `openclaw`; omission means development verification
only. An opted-in command may use `{application_root}`, which registry
generation translates to the selected `{artifact_root}`, but it may not use
development-only `{repository_root}` or `{diagnostics}` placeholders.
Duplicate plugin IDs or destinations are invalid. The generated marketplace
contains `.obvious-one-validation.json` as the normalized plugin-validation
registry and `tools/verify_marketplace.py` as the self-contained verifier; the
workflow uses these files rather than embedding named-plugin assertions.

Reports are immutable JSON artifacts below caller-selected staging, `dist`, or
`.tmp` locations. The framework introduces no database, daemon state, or
developer-global configuration.

## 9. Services and Integrations

The framework has no required network service. Python 3.11 or newer and a
compatible local Git executable are the only new orchestration prerequisites.

Git integration uses argument-vector subprocess calls, never a shell command
string. It has explicit timeouts, captures output, validates return codes, and
does not fetch, pull, push, reset, clean, or modify user configuration.

GitHub Actions integration is generated YAML using pinned major action
versions already accepted by the marketplace. Its required matrix is Windows,
Ubuntu, and macOS with Python 3.11. Network-dependent installation, release,
and registry operations remain outside the validation workflow.

ClawHub commands are not invoked by generic validation unless a future,
separately approved publication workflow consumes an enabled and compatible
ClawHub contract. This design removes the assumption that `bundle-plugin`
implies a native ClawHub manifest.

## 10. Workflow Specification

The generic state progression is:

```text
DISCOVERED
    -> VALIDATED
    -> STAGED
    -> ARTIFACT_VERIFIED
    -> GIT_VERIFIED
    -> READY_FOR_REVIEW
```

Any state may terminate as `BLOCKED` for a missing owner decision or `FAIL` for
invalid, unsafe, or mismatched evidence. A downstream stage is `NOT VERIFIED`
when its prerequisite did not pass.

Build workflow:

1. Parse and version-route the contract.
2. Confine source and output paths.
3. Expand the inventory and resolve exactly one policy per candidate.
4. Validate rights and publication declarations.
5. Create an isolated temporary stage.
6. Canonicalize or copy each approved file according to policy.
7. Add declared framework-generated files and overlays.
8. Run generic and application audits.
9. Write and reverify the content manifest.
10. Atomically replace the requested output and remove the prior backup.

On failure before step 10, the previous output is untouched. On replacement
failure, the previous output is restored when possible and the operation is
`FAIL`. There are no automatic retries for deterministic validation failures.

Marketplace workflow:

1. Validate every selected application and catalog identity.
2. Copy the marketplace baseline to a new staging tree, build only entries in
   `build` mode, and verify without rebuilding entries in `verify_existing`
   mode.
3. Generate catalogs, exact-byte attributes, verifier, CI, and delta report.
4. Verify staging-tree bytes.
5. Optionally verify a separately prepared Git index, commit, and clean
   checkout.
6. Stop at `READY_FOR_REVIEW`; never apply, commit, push, tag, or publish.

## 11. Quality Attributes

- **Determinism:** two builds from identical logical inputs in independent
  temporary roots produce byte-identical artifacts and reports except fields
  explicitly defined as external evidence, such as a selected commit ID.
- **Cross-platform compatibility:** canonical artifacts and fresh checkout
  bytes agree on Windows, Linux, and macOS. Host path separators and file
  enumeration order cannot affect output.
- **Reliability:** output replacement is transactional; failed operations list
  their attempted mutations and cannot invalidate the last verified artifact.
- **Observability:** every result has stable status, code, diagnostics,
  artifacts, mutation records, and per-gate evidence.
- **Maintainability:** framework modules remain small and single-purpose;
  public interfaces are documented and private helpers are not marketplace
  dependencies.
- **Performance:** inventory, hashing, and Git verification stream files and
  remain linear in artifact byte size. No design requirement justifies loading
  a full large binary into memory.
- **Compatibility:** schema v1/v2 inspection and legacy verification remain
  supported. New builds require schema v3. Existing non-distribution public
  APIs remain compatible unless an implementation plan identifies and tests a
  necessary transition.
- **Accessibility and localization:** not applicable because the framework has
  no user interface. JSON codes remain locale-neutral for clients and
  orchestrators.

## 12. Security and Privacy

- All contract, inventory, artifact, report, and marketplace paths are
  confined to explicitly supplied roots after resolution.
- Symlinks, junctions, and other reparse points are rejected at distribution
  boundaries.
- File patterns cannot escape a root, and case-folded destination collisions
  are rejected for cross-platform safety.
- Existing forbidden-name and secret-fragment audits remain mandatory and gain
  tests for normalized text and binary classifications.
- Product audit hooks execute only when explicitly declared inside the
  application root; their failures are contained and reported.
- Reports omit credentials, environment variables, user names, private
  absolute paths, and source document contents.
- Rights approval is declarative evidence, not inferred from file type,
  location, or source ownership. Missing evidence blocks redistribution.
- The framework validates the presence and shape of approval evidence; it does
  not authenticate a human caller or adjudicate the decision owner's legal
  authority.
- Marketplace preparation is deny-by-default and writes only to a separate
  validated staging root.
- Git integration is read-only for the supplied marketplace and never invokes
  remote or destructive commands.

## 13. Validation and Acceptance

Implementation is test-first. Failing tests are committed or observed before
the corresponding production change.

### Contract and recovery acceptance

- **FRH-A01 / FRH-001:** v1/v2 contracts parse for inspection and legacy
  verification; build and marketplace preparation return
  `legacy_contract_read_only`.
- **FRH-A02 / FRH-001:** a valid schema-v3 contract builds successfully.
- **FRH-A03 / FRH-002, FRH-003:** zero or multiple policy matches return
  `unclassified_files` or `ambiguous_file_classification` before output
  mutation.
- **FRH-A04 / FRH-003:** missing rights evidence returns `rights_unresolved`
  and leaves the previous valid artifact byte-identical.
- **FRH-A05 / FRH-004:** every command emits a valid result-schema-v1 envelope
  for success, blocked, malformed-input, audit, Git, and I/O cases.
- **FRH-A06 / FRH-001:** migration never overwrites its input or an existing
  destination and never fabricates unresolved decisions.

### Byte and artifact acceptance

- **FRH-A07 / FRH-002:** CRLF and CR application text inputs produce the same
  LF artifact bytes as equivalent LF input.
- **FRH-A08 / FRH-002:** binary inputs are copied byte-for-byte.
- **FRH-A09 / FRH-002:** generated JSON has sorted keys, LF endings, and one
  final newline.
- **FRH-A10 / FRH-006:** two isolated builds have identical file bytes,
  manifests, aggregate identities, and relative-path reports.
- **FRH-A11 / FRH-003:** audit, secret, link, size, or manifest failure cannot
  replace an earlier verified output.

### Marketplace and CI acceptance

- **FRH-A12 / FRH-005:** marketplace preparation changes only a separate
  staging root and reports the exact proposed delta.
- **FRH-A13 / FRH-006:** staged bytes, Git index blobs, committed blobs, and
  fresh-checkout bytes all match the manifests under simulated or native
  Windows, Linux, and macOS configurations.
- **FRH-A14 / FRH-006:** the historical LF-manifest/CRLF-checkout mismatch is a
  generic regression fixture and is rejected without any product identity in
  framework production code.
- **FRH-A15 / FRH-007:** every plugin present in the required catalogs appears
  exactly once in the generated plugin-by-OS matrix.
- **FRH-A16 / FRH-007:** adding a synthetic catalog plugin automatically adds
  validation cells without editing workflow logic.
- **FRH-A17 / FRH-008:** disabled ClawHub publication is `NOT APPLICABLE`;
  enabled but incomplete or incompatible native publication is `FAIL`.
- **FRH-A18 / FRH-009:** Vibe Coding Designer passes its application suite and
  generic marketplace validation without hard-coded Vibe behavior in generic
  modules.
- **FRH-A19 / FRH-010, FRH-011:** API and CLI operations require no human
  identity or interactive input and return identical results for identical
  explicit inputs whether invoked by a script, agent, CI job, client, or human.
- **FRH-A20 / FRH-001, FRH-005, FRH-007:** a schema-v3 `build` entry may replace
  only its staged artifact paths, while a schema-v1 or schema-v2
  `verify_existing` entry receives generic CI coverage and remains byte-for-byte
  unchanged; using a legacy contract with `build` returns
  `legacy_contract_read_only`.

### Required verification commands and evidence

The implementation plan must include, at minimum:

- focused unit and integration tests for each preceding acceptance case;
- `python -B -m unittest discover -s .\tests\framework -v`;
- affected top-level repository tests;
- `python -B -m unittest discover -s .\applications\vibe-coding-designer\tests -v`;
- two isolated schema-v3 builds and byte comparison;
- a locally prepared marketplace delta and Git-blob/fresh-checkout audit;
- `git diff --check` and proof that verification left tracked files unchanged.

Marketplace CI must provide Windows, Ubuntu, and macOS evidence. A local host
run may be `PASS` without remote OS evidence, but release readiness remains
`NOT VERIFIED` until all required matrix cells pass.

## 14. Assumptions and Open Questions

### Confirmed decisions

- Schema v3 is mandatory for new distribution builds; v1/v2 are read-only
  legacy formats.
- The framework is non-interactive and machine-readable. Guided recovery is a
  client or orchestrator responsibility.
- Unclassified files block the build and trigger structured recovery
  diagnostics; the framework never silently chooses a disposition.
- GitHub marketplace and ClawHub are separate publication surfaces.
- Vibe Coding Designer is the first generic-CI integration case.
- Cool Bible Tutor migration and ClawHub resolution are separate follow-up
  work; until then its preparation-catalog entry uses `verify_existing`.
- The current work prepares local changes only and does not publish.

### Assumptions

- Python 3.11+ remains the framework host requirement.
- Git is available wherever Git-blob or fresh-checkout verification is
  requested; artifact-only commands do not require Git.
- Marketplace catalogs remain the authoritative registered-plugin inventory.
- Application configuration schema v2 is not automatically renamed or
  migrated merely because the separate distribution contract advances to
  schema v3.

### Open questions

None block implementation planning. Module placement may be refined without
changing the public CLI, schema fields, semantics, requirements, or acceptance
criteria above. Any change to those contracts, dispositions, byte semantics,
legacy write restrictions, publication boundaries, or supported runtimes
requires renewed owner approval.
