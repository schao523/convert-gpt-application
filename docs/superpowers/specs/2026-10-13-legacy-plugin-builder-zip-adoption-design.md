# Legacy Plugin Builder ZIP Adoption Design

**Status:** Owner-approved design recorded for written review

**Date:** 2026-10-13

**Repository:** `convert-gpt-application`

**Initial artifact:** `Vibe_StorySpirit_Director_v1.0.2.zip`

**Initial artifact SHA-256:** `01284edd379ed97e09e8d6bac08d2009d9b2f460ea3654d03f167a1d31305633`

**Target:** Obvious One Codex marketplace

## 1. Purpose

Extend the existing Plugin Builder ZIP onboarding boundary to recognize one
older, deterministic Plugin Builder output profile that predates
`PLUGIN-BUILDER-MANIFEST.json` and the external `package-metadata.json`
sidecar. The extension permits Workbench to adopt the exact historical ZIP
without rebuilding or silently repairing it.

The initial artifact was generated by Plugin Builder and contains a portable
manifest pair, `CONTENT-MANIFEST.json`,
`docs/candidate-content-manifest.json`, and
`docs/verification-report.json`. Those records are useful producer evidence,
but they are not the later Plugin Builder v2/v3 authority envelope. Workbench
therefore supplies a separate, owner-approved adoption record that binds the
exact archive while preserving the distinction between producer claims,
Workbench observations, and owner publication authority.

Success means that the existing `prepare-plugin-zip-marketplace` command can
produce the same deterministic, publication-neutral onboarding proposal used
for current Plugin Builder packages. Success does not publish the plugin,
change any ZIP member, or promote unobserved runtime behavior.

## 2. Selected Design

Add a narrow input contract named
`workbench-legacy-plugin-builder-adoption-v1`. It is an external Workbench
authority record for a recognized historical Plugin Builder package profile.
It is not fabricated Plugin Builder metadata and must never be presented as
`plugin-builder-package-v2` or `plugin-builder-package-v3` evidence.

The selected flow is:

1. safely inventory and inspect the immutable historical ZIP;
2. recognize the exact legacy Plugin Builder deterministic-content profile;
3. close the owner-approved adoption record against the archive and its
   internal manifests;
4. validate the separate publication-decision record;
5. materialize a deterministic Workbench application proposal whose
   `imported-plugin/` tree preserves every source member byte; and
6. continue through the unchanged application and marketplace pipelines only
   after the proposal is separately adopted.

Generic legacy ZIP acceptance, heuristic producer inference, and silent
content repair remain prohibited.

## 3. Scope

### 3.1 Included

- Flat, single-root ZIPs generated by an earlier Plugin Builder release.
- A required root `plugin.json` and `.codex-plugin/plugin.json` pair.
- A required `CONTENT-MANIFEST.json` with format
  `deterministic-content-manifest-v2`.
- A required `docs/candidate-content-manifest.json` with format
  `candidate-content-manifest-v2`.
- A required `docs/verification-report.json` whose plugin identity and version
  match the manifest pair.
- Exact archive, member, internal-manifest, and content-tree closure.
- A separate owner-approved Workbench adoption record.
- Reuse of the existing publication decisions, deterministic proposal,
  application registration, marketplace preparation, and verification flow.
- Codex publication to Obvious One; OpenClaw and ClawHub remain not applicable
  to this bounded onboarding profile.

### 3.2 Excluded

- ZIPs not demonstrably matching the recognized historical Plugin Builder
  profile.
- Archives with `PLUGIN-BUILDER-MANIFEST.json`,
  `WORKBENCH-REPAIR-MANIFEST.json`, or another competing semantic authority.
- Treating internal historical reports as current v2/v3 package metadata.
- Adding, deleting, normalizing, or rewriting source ZIP members.
- Inferring license, redistribution rights, third-party-content disposition,
  public-marketplace approval, or runtime validation.
- OpenClaw conversion, ClawHub release, OpenAI universal-directory submission,
  Git push, pull request, merge, tag, or release.
- Updates or replacements of an existing Workbench or marketplace plugin ID.

## 4. Authority and Evidence Model

The inputs have distinct authority roles:

| Input | Authority |
| --- | --- |
| Historical Plugin Builder ZIP | Exact source bytes proposed for adoption |
| Internal deterministic manifests | Producer-declared inventory and candidate claims, independently checked where possible |
| `workbench-legacy-plugin-builder-adoption-v1` | Owner authority for Workbench to adopt this exact historical artifact |
| `plugin-publication-decisions-v1` | Owner authority for license, redistribution, third-party content, target, and public marketplace |
| Workbench inspection | Current static observations derived from the supplied bytes |
| Workbench proposal | Derived registration only; no authority to alter application behavior |

The adoption record is not a signature and does not authenticate the
historical producer. It authorizes Workbench to rely on the exact supplied
bytes after independent closure checks. Archive origin, filename, caller
identity, installed-cache presence, and historical chat statements are never
substitutes for the record.

Historical verification statements remain under `producer_claims`.
Workbench may report the validated package structure as
`STATICALLY VERIFIED`, while installation, skill invocation, capability
discovery, deterministic operation execution, result delivery, conversation
behavior, and cross-runtime equivalence remain `NOT VERIFIED` unless a
separately supported identity-bound evidence input proves them.

## 5. Adoption Contract

The JSON document uses schema
`workbench-legacy-plugin-builder-adoption-v1` and contains exactly:

- `schema`;
- `input_profile`, fixed to
  `PLUGIN_BUILDER_DETERMINISTIC_CONTENT_V2`;
- `plugin_id`;
- `version`;
- `archive_sha256`;
- `member_manifest_sha256`;
- `members`, an ordered array of exact `path`, `size`, and `sha256` records;
- `content_tree_sha256`;
- `content_manifest_path`, fixed to `CONTENT-MANIFEST.json`;
- `content_manifest_sha256`;
- `candidate_manifest_path`, fixed to
  `docs/candidate-content-manifest.json`;
- `candidate_manifest_sha256`;
- `verification_report_path`, fixed to
  `docs/verification-report.json`;
- `verification_report_sha256`;
- `executable_files`, the exact approved executable member paths;
- `dependency_files`, the exact approved dependency-declaration member paths;
- `adoption_approved`, required to be `true`;
- `confirmed_by`;
- `decision_recorded_at`; and
- `purpose`, fixed to `OBVIOUS_ONE_CODEX_MARKETPLACE_ONBOARDING`.

Unknown and missing fields fail closed. `adoption_approved: false` or missing
owner identity is `BLOCKED`. Invalid schema, identity, hashes, inventory, or
paths are `FAIL`.

`decision_recorded_at` is retained as evidence but excluded from deterministic
proposal identity. The remaining fields participate in the adoption-record
digest. The archive digest, member list, and internal authority hashes make an
approval non-transferable to another ZIP or version.

The separate `plugin-publication-decisions-v1` contract remains unchanged.
Adoption approval does not imply MIT licensing, redistribution approval,
third-party-content review, or public-marketplace approval.

## 6. CLI Contract

Extend the existing command with a mutually exclusive legacy input:

```powershell
python -B -m obvious_one_plugin_framework.cli prepare-plugin-zip-marketplace `
  --archive .\path\legacy-plugin-builder.zip `
  --legacy-adoption .\path\legacy-adoption.json `
  --publication-decisions .\path\publication-decisions.json `
  --repository D:\GitHub\convert-gpt-application `
  --output .\.tmp\plugin-onboarding\<plugin-id> `
  --json
```

Exactly one of `--package-metadata` and `--legacy-adoption` is required.
`--evidence` remains available only for current Plugin Builder v2/v3 metadata
until a later design defines an identity-compatible legacy evidence format.
Supplying `--evidence` with `--legacy-adoption` fails as unsupported rather
than silently ignoring it.

Result-schema and exit semantics remain unchanged:

- `PASS` / exit 0 for a deterministic proposal;
- `BLOCKED` / exit 2 for missing owner authority or a recognized unresolved
  decision;
- `FAIL` / exit 3 for unsafe, inconsistent, tampered, ambiguous, or unsupported
  inputs; and
- exit 4 for local I/O or environment failure.

The command writes only to its owned proposal output. It does not modify the
source archive, tracked Workbench application tree, marketplace checkout, or
Git state.

## 7. Recognition and Validation

### 7.1 Envelope recognition

The legacy profile is recognized only when all of these conditions hold:

- the archive resolves to one safe flat plugin root;
- root `plugin.json` and `.codex-plugin/plugin.json` exist;
- all three required internal evidence files exist at their fixed paths;
- no `PLUGIN-BUILDER-MANIFEST.json`, `WORKBENCH-REPAIR-MANIFEST.json`, or other
  recognized authority manifest is present; and
- the external adoption record closes against the exact archive.

A package satisfying a current v2/v3 or repair profile must use that existing
profile. Mixed authority returns `onboarding.inspection.authority_ambiguous`.
An archive with no recognized profile returns
`onboarding.inspection.authority_unknown`.

### 7.2 Archive and manifest closure

Reuse the existing safe archive inventory and extraction APIs. Validate:

- archive SHA-256, ordered member inventory, member digest, and content-tree
  digest;
- no unsafe path, alias, case-fold collision, file/directory collision, link,
  reparse point, forbidden name, compression-limit breach, or unexpected
  envelope prefix;
- `CONTENT-MANIFEST.json` lists every other archive member exactly once with
  matching path, size, and SHA-256 and declares the matching plugin ID,
  version, file count, and format;
- `docs/candidate-content-manifest.json` uses its declared self/package
  exclusions and otherwise closes over the same candidate members;
- the adoption record hashes all three required internal evidence files;
- the portable and OpenAI compatibility manifests agree on all overlapping
  identity and interface fields; and
- plugin ID and version agree across manifests, internal reports, adoption
  record, and publication decisions.

The historical portable manifest is allowed to omit later interface fields
such as `developerName`, `capabilities`, `longDescription`, and `category`
when those fields did not exist in that manifest profile. A field present in
both manifests must match. Missing historical fields are not synthesized into
the imported plugin and do not relax validation for current v2/v3 packages.

### 7.3 Public-content audit

Never execute imported scripts during intake. Scan the extracted tree using
the existing secret, credential, development-import, dependency, executable,
and path policies. The observed executable and dependency file sets must equal
the approved sets in the adoption record.

An executable listed by the archive but omitted from the adoption record, or
an approved executable no longer present in the archive, is `FAIL`. Approval
of a path records awareness of its inclusion; it is not runtime execution
evidence.

### 7.4 Producer claims and Workbench observations

Preserve these historical statements under `producer_claims`:

- internal manifest formats and identities;
- candidate logical digest, verification stage, and blocking-failure count;
- source handoff and baseline claims; and
- any producer-declared reference-consultation results.

Do not map historical phrases such as `STATICALLY/LOCALLY VERIFIED` to
installed-runtime evidence. Workbench records current archive validation under
its own evidence fields and sets every installed-runtime layer to
`NOT VERIFIED` for this profile.

## 8. Proposal and Exact-Byte Preservation

Reuse the current onboarding proposal model and generated application layout.
The `imported-plugin/` tree contains every source archive member with identical
bytes and no additional file. Generated Workbench policy, license, privacy,
security, source-decision, distribution, test, and build files live outside
that immutable subtree.

The generated Codex marketplace builder copies the allowlisted imported
members without normalization. If marketplace-owned legal or installation
files are required at the published plugin root, their provenance and hashes
are declared separately and they may not collide with an imported path.
No generated overlay may replace or reinterpret an imported manifest,
reference, script, or skill.

The proposal records:

- the adoption-record digest;
- exact archive and member identities;
- all historical producer claims;
- all Workbench-derived observations;
- `STATICALLY VERIFIED` only for the layers actually checked;
- `NOT VERIFIED` for all installed-runtime layers; and
- OpenClaw and ClawHub as `NOT APPLICABLE` under this bounded contract.

Byte-identical inputs and equivalent owner decisions produce byte-identical
proposal trees. Machine-specific absolute paths and decision timestamps are
excluded from deterministic identity.

## 9. Compatibility and Failure Semantics

- Current Plugin Builder v2/v3 packages continue through
  `--package-metadata` with no behavior change.
- Workbench-repaired packages continue through their existing metadata path.
- Existing legacy candidate-v1 inspection behavior remains unchanged.
- The new profile is selected only by the explicit `--legacy-adoption`
  contract and never by heuristic fallback.
- An existing Workbench application, catalog entry, or marketplace plugin ID
  remains `BLOCKED`; this contract cannot authorize replacement.
- Failed validation preserves any previous valid proposal byte-for-byte.
- Diagnostics remain stable, deterministic, and path-redacted.
- Missing adoption or publication authority is `BLOCKED`; tampering,
  ambiguity, unsafe content, and inconsistent evidence are `FAIL`.

## 10. Testing Strategy

Use test-driven implementation in the canonical Windows environment and
isolated genuine system-temporary roots. Cover:

1. the exact StorySpirit 1.0.2 profile as a representative fixture;
2. valid deterministic-content-v2 inventory and candidate-manifest closure;
3. archive, member, tree, content-manifest, candidate-manifest, verification,
   manifest-pair, identity, executable, and dependency tampering;
4. missing and false adoption authority;
5. mixed current, legacy, and repair authorities;
6. unknown historical profiles and malformed internal formats;
7. portable-manifest historical omissions versus contradictory shared fields;
8. unsafe archive members, links, reparse points, aliases, case collisions,
   forbidden names, credentials, and development-only imports;
9. exact imported-byte preservation and overlay collision rejection;
10. deterministic repeated proposal generation;
11. unsupported legacy `--evidence` and mutually exclusive CLI inputs;
12. unchanged v2, v3, candidate-v1, and repaired-package behavior;
13. generated application tests, schema-v3 Codex distribution, and secret
    audit;
14. end-to-end adoption followed by the existing marketplace filesystem,
    index, commit, and fresh-checkout verification gates; and
15. confirmation that intake and proposal generation never mutate source,
    tracked applications, marketplace baselines, or Git.

After each red-green cycle, run the smallest affected regression set. Run the
complete framework and repository contract suites before completion. Test the
generated artifact rather than only development source.

## 11. Publication Sequence

Implementation of this contract does not itself publish StorySpirit. After
the feature passes verification:

1. create and review the exact adoption record for the source SHA-256;
2. obtain explicit MIT, redistribution, third-party-content, and public
   Obvious One decisions in `plugin-publication-decisions-v1`;
3. generate and review the onboarding proposal;
4. separately approve proposal adoption into Workbench;
5. run product, contract, deterministic-build, and repository verification;
6. prepare and verify an isolated marketplace delta;
7. review the exact marketplace diff and artifact hashes;
8. obtain marketplace mutation authorization;
9. push a scoped branch and create a pull request;
10. require targeted cross-platform CI to pass;
11. obtain merge authorization; and
12. verify the post-merge `main` workflow.

No step authorizes OpenClaw, ClawHub, an OpenAI directory, or another registry.

## 12. Acceptance Criteria

The compatibility feature is complete when:

- the exact StorySpirit 1.0.2 ZIP can be closed by an approved legacy Plugin
  Builder adoption record without modifying any source member;
- an arbitrary legacy ZIP without that exact contract remains fail-closed;
- no historical claim is relabeled as v2/v3 or runtime-verified evidence;
- current v2/v3 and repaired-package onboarding remain unchanged;
- missing rights or publication decisions block proposal generation;
- the deterministic proposal imports every source member byte-for-byte;
- generated application and marketplace artifacts pass their applicable
  structural, security, deterministic, and exact-byte gates;
- complete framework and repository contract suites pass;
- the command performs no Git or marketplace mutation; and
- publication remains pending until the separate owner decisions and remote
  authorizations in Section 11 are satisfied.

For the initial StorySpirit artifact, a successful local onboarding result is
reported as `STATICALLY VERIFIED` and
`CONVERSION COMPLETE — RUNTIME VALIDATION PENDING`, not `READY`.
